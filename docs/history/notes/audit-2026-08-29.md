# SymCE audit, 2026-08-29

Five adversarial review passes over `symce/src/hook.c` and `symce/src/main.c`, each with a
different lens: eZ80 correctness, TI token encoding, context safety, installer lifecycle,
and engine-integration risk. 44 findings, 43 unique.

Triaged below against what is now in the tree. Everything marked FIXED has a commit and,
where the logic is testable off-calculator, a check in `make -f pc.makefile test`.

## Fixed

| Severity | Finding | Fix |
|---|---|---|
| critical | Every TI-BASIC and ASM program launch from the home screen was replaced with `4X` | `0x5F` (prgm) rejected by the whitelist scan |
| critical | STO was destroyed: no variable could be stored from the home screen | `0x04` (STO) rejected |
| critical | 27 second-bytes of the `$BB` table in `$41..$5B` are real tokens - `DelVar`, `ClrAllLists`, `GetCalc(`, `Select(` | all two-byte lead bytes rejected |
| high | 27 second-bytes of the `$EF` table likewise - every colour, `Image1`..`Image0` | same |
| high | `$5F prgm<name>` and `$EB list<name>` are followed by raw letter tokens | same |
| medium | `$5E $41..$45` are `r2T`..`r6T` | same |
| critical | Letter tokens inside a string literal are text, not variables; the hook re-triggered on its own output | `0x2A` (tString) rejected, so a recalled result passes through |
| critical | `.Lhit` wrote 4 bytes at editTop with no bounds check | guard: editBtm must exceed editTop by at least 4 |
| critical | No editOpen check: ENTER on a blank home screen scanned stale pointers | gate 4 on editFlags (`iy+1` = `0xD00081`) bit 2 |
| medium | Both scan loops terminated only on exact pointer equality, so an inverted pair walked the 24-bit address space | empty-or-inverted segments are skipped |
| high | Installer silently uninstalled another program's homescreen hook and reported the calculator as stock | previous pointer and enable bit saved to `SYMCEPV`, restored on disarm |
| critical | Installer never checked the armed pointer was actually in flash, so a silently failed archive armed a RAM address | refuses to arm unless the pointer is below `0xD00000` and the body still starts with `0x83` |
| medium | "Archive full?" was the one failure `get_hook` could not report | replaced with the three causes that really produce NULL |

Ten of the thirteen criticals are closed.

The whitelist is the load-bearing change. The scan used to look for any byte in `0x41..0x5B`
and treat it as a variable. TI tokens are variable length, so that cannot distinguish a
standalone token from the second byte of a two-byte one - 59 sequences counted against
CEdev's own `ti/tokens.h`. It now accepts only tokens `symcore`'s `ti_table` can parse and
aborts to stock on anything else. `tools/classify_test.c` mirrors the classifier range for
range and checks it against both `ti_table` and the lead-byte list.

## Still open, needs facts we do not have yet

| Severity | Finding | What is needed |
|---|---|---|
| critical | ENTER while scrolled into the entry history means "paste", not "execute". The hook rewrites the entry line anyway | which OS flag distinguishes the two |
| high | `progExecuting` is not checked, so BASIC `Input`/`Prompt` is protected only by the `cxCurApp` gate | confirm the flag byte; `ti84pce.inc` lists `progExecuting equ 1` under `newDispF equ 8h`, but `allowProgTokens` is also bit 1 of that byte, so the equate is ambiguous |
| medium | Menu and catalog overlays leave `cxCurApp` at `cxCmd`, so ENTER on a menu item can rewrite the entry underneath | a distinguishing flag |

All three are the same shape: the current gates say "the home screen is the current context",
which is not the same as "the user just pressed ENTER to evaluate an expression they typed".

## Known hazard, no fix available from where we stand

Archive garbage collection relocates `SYMCEHK`, and `homescreenHookPtr` is never revalidated.
The CE toolchain's own documentation for `ti_GetDataPtr` says so outright: *"variables may be
shifted around in memory, causing this pointer to become invalid"*, and `ti_SetArchiveStatus`
carries *"archiving a variable can cause a garbage collection cycle"*.

Once the OS calls a stale pointer there is nothing the hook can do - it is already executing
whatever now occupies that address. Mitigations in the tree: the installer refuses to arm a
pointer that is not in flash or has lost its magic byte, and the status screen says to re-run
SYMCE after archiving, unarchiving or sending anything. A real fix means either a hook manager
that revalidates (Cap'n Hook's job, blocked on fasmg) or not putting the body in archive.

## Engine integration

Seven findings, all critical or high, converge on one conclusion: the engine cannot run inside
the hook.

- Copy-and-jump is impossible. The CE linker has no PIC mode and eZ80 has no PC-relative data
  addressing, so compiled C runs at the address it was linked for. Confirmed independently
  from `~/CEdev/meta/linker_script.ld`.
- `symcore` uses libc malloc, whose heap is a link-time absolute range that sits in the OS's
  screen shadow buffers.
- Allocation is not permitted while the edit buffer is open, so the engine cannot be loaded
  during the hook at all.
- 78,560 bytes needed against roughly 69,090 bytes of contiguous safe RAM.
- ~4 KB of stack, entered several frames deep, against unbounded CAS recursion.
- The CE C startup and exit sequences are not callable from a hook.
- Identity tables cache heap pointers in `.data` and are never unloaded, so a reused arena is
  a use-after-free.

Spec section 6 chose "copy the engine from archive into a RAM arena and jump to it". That does
not survive. The recommendation from the audit is to rewrite the edit buffer so the OS
*launches* the engine as an ordinary program, which then has ordinary program resources. That
is under research before the spec is rewritten.

## Refuted

Six findings were re-checked by independent verifiers and dismissed. All but one were dismissed
as **already fixed at HEAD** - the fixes above landed while the audit was still running, and the
verifiers re-read the file. That is corroboration rather than contradiction.

The exception is the `.Lhit` overrun, which one verifier argued cannot occur because the claim's
premise about the OS - that the home-screen edit gap is zero at rest - is backwards. The bounds
guard went in anyway; it costs nine bytes and does not depend on who is right.

## Not worth fixing

- `A` is clobbered on the pass path for key events. The pass path ends in `cp a, a`, which sets
  Z regardless, and the contract only reads the flag.
- Disarm's read-modify-write on `0xD000B4` is non-atomic across a byte holding six hook-enable
  bits. There is no concurrency on this machine.

## Addendum, 2026-08-30: three findings above are wrong

A later research pass overturned parts of this document. Recorded here rather
than silently edited, because the reasoning matters.

**"The engine cannot run inside the hook" was wrong.** The blocking claim was
"you may not allocate memory while the edit buffer is open". The real rule is
narrower: `editTop`/`editCursor`/`editTail`/`editBtm` point into user RAM, and
`_InsertMem`/`_DelMem`/VAT operations shift that region without fixing them up.
An arena at a link-time absolute address outside user RAM performs no OS
allocation at all, so the rule does not apply to it. The deciding constraint
turns out to be the *display*, not memory: the only way to get a right-aligned
answer into stock MathPrint history is to have it in the edit buffer before the
OS parses, which means the CAS must finish before the hook returns.

**"No OS calls in the hook body" was too strict.** Position independence forbids
absolute references to *ourselves*. Absolute OS entry points are fixed addresses
and stay valid wherever the body is copied. `call 0x02050C` is fine. The rule
that survives is that the body executes from flash and so must not trigger a
garbage collect.

**The archive-GC hazard is fixable after all.** This document called it
unfixable. It is not: look the appvar up from inside the hook with `_Mov9ToOP1`
(0x020320) + `_ChkFindSym` (0x02050C) rather than caching a pointer at install
time. That follows directly from the previous correction.

**And one new critical defect nobody logged.** After the rewrite, Ans holds a
`StrngObj` (tag 4), so `Ans+1`, `2Ans` and `Ans*2` all raise ERR:DATA TYPE, and
ENTER on an empty entry line re-runs the string `"4X"` instead of the original
expression. That is a stock workflow broken semi-silently, and it is inherent to
the string-literal delivery mechanism rather than to any bug in the current code.

Full research at `research-2026-08-30-architecture-and-speed.md`.
